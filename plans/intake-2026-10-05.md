## 4. Bugs

**D1. A command Todoist refuses is logged and then treated as done.** `todoist_run_commands` (`app.py:223-231`) logs a `sync_status` value other than `ok` and returns normally. The read-back on 2026-10-05 showed Todoist does refuse single commands inside an HTTP 200 answer (a fractional radius, a name over 255 characters). Reproduced against a local stub that refuses adds:
- Webhook: answers 200, no reminder exists, Todoist does not redeliver.
- Edit: the delete succeeds and the re-add is refused; the route answers 302, the mapping is updated, and the reminder is gone for good.
- Delete with a refused delete (subagent's run): the mapping row is removed and the reminder is stranded.

#40 closed the two refusals found so far. What can still be refused: the account's location-reminder limit (`max_reminders_location` in the plan limits), a task deleted between the read and the write, coordinates that are not numbers (D6), and a saved row whose name is over 255 characters (D9). Fix: raise from `todoist_run_commands` when any status is not `ok` (the callers already turn that into 503 or 502), and stop the edit from deleting before it knows the add worked, either with `reminder_update` in place (documented for the sync endpoint, untried here) or by sending adds first and deletes only when every add was accepted. Tests through `fake_todoist` with a refusal switch. Effort S to M. Confidence HIGH. The webhook half predates #39; the sweep half came with it.

**D2. Two labels mapped to the same place fight over one reminder.** Matching is by name, trigger and radius, and nothing stops two labels from sharing all three; the form's default radius of 100 makes that easy for one address. Reproduced:
- Webhook (`app.py:528-533`, then `:541`): a task carrying only label A has its reminder deleted because it also matches unused label B, and the add is then skipped because the list read before the delete still contains it. Four webhooks in a row gave present, absent, present, absent. This half predates all three intakes.
- Sweep (`app.py:277-291`): deleting mapping B removed the reminder of a task that carries only A. Editing B would move it to B's new address. Introduced by #39. It repairs itself at that task's next update; the webhook half never does.

Fix: in the webhook, do not delete a reminder that matches a mapping whose label is on the task; in the sweep, leave reminders alone when another mapping of the same user has the same place. Or refuse a second mapping at an identical place. Effort S. Confidence HIGH.

**D3. A stall while connecting is retried three times.** `Retry(total=3, read=0, ...)` at `app.py:111-113` leaves `connect` unset, so it falls back to `total`. Measured here against an unroutable address with the app's own policy and a 0.5 s timeout: `ConnectTimeout` after 8.0 s, which is 4 attempts plus 6 s of waits. At the production timeout that is 46 s (computed, not measured), past gunicorn's 30 s. The effect is the one C2 described: the only worker is killed mid-request, and if that request was a sweep it may be half applied (D4). A refused connection fails fast and is not affected; this needs packets to be dropped. Fix: `connect=0`, or `timeout=(3, 10)`. Effort S. Confidence HIGH on the mechanism; never observed.

**D4. A sweep that fails after its first batch leaves reminders moved and the mapping unchanged.** Commands go out 100 per request (`app.py:225-226`); if a later request raises, the route answers 502 and keeps the old mapping (`:437-443`), but the earlier batches were applied. Those reminders now sit at the new place; the next webhook for their tasks adds a second reminder at the old place. Submitting the same edit again recovers. It needs more than 50 tagged tasks on one mapping for an edit, or more than 100 for a delete. `sweep_reminders`' docstring admits the "between batches" case; nothing tells the user to resubmit. Fix: say so in the 502 answer, or commit the mapping once any batch has applied. Effort S. Confidence HIGH that it happens, LOW that an account this size meets it.

Low:
- **D5.** Every webhook does a full sync to read reminders (`app.py:192-195`, `sync_token="*"`). Todoist documents a limit of 100 full syncs per user per 15 minutes. More than 100 task changes in that time would draw 429s, each retried three times, then 503 and a redelivery 15 minutes later. `GET /api/v1/location_reminders?task_id=` is documented and would read one task's reminders without a full sync. Documented, unobserved.
- **D6.** `lat` and `long` accept `nan`, `inf` and out-of-range values (`app.py:418-419`). With `nan` the "unchanged" check at `:436` is always false, so every resubmit sweeps, and the coordinates go to Todoist as text. Only the user's own data is affected.
- **D7.** Retyping the address without picking a suggestion keeps the previous suggestion's coordinates (`templates/index.html:277-282` sets them only on `place_changed`), so the name and the location can disagree. Predates the diff.
- **D8.** The mapping list prints the stored radius (`templates/index.html:165`), not the one in force. A row saved at 300 shows "300.0 M" while its reminders use 255. Whether such rows exist is not known (section 2).
- **D9.** `place_of` caps and strips, but a saved name over 255 characters is sent as is and refused, and a saved radius below 1 becomes 0, which is untested against Todoist. Only rows saved before #40 can be like this.

## 6. Opinions

- **Reject or clamp.** #40 answers 400 to a radius above 255. Clamping to 255 and saying so on the page would have been the "warn over reject" reading of 2.21. With the number input capped at 255 a browser user never reaches the 400, which is a bare error page that loses the form.
- The radius prints as "100.0 M" because the column is a float.
- `from urllib3.util.retry import Retry` (`app.py:24`) imports a package that is only a transitive dependency.
- Test literals still say `250.0` and `100.0` where the code now sends integers (`tests/test_routes.py:216`, `tests/test_webhook.py:39`). They pass because the numbers are equal; Todoist accepts both forms.
- `test_delete_own_mapping` and `test_deleting_a_mapping_removes_its_reminders` overlap; the second covers the first.
- Carried from the second report: `session["oauth_secret_state"]` is never removed (`app.py:345`); the token exchange sends `/authorize` as its redirect URI (`:358`); CI deploys on documentation-only merges, this report included; `uv:latest` and `setup-flyctl@master` are unpinned; Bootstrap 4.0.0-beta.2.

## 8. Standards feedback

1. **A fake that echoes certifies nothing about the remote.** v79 shipped with 37 green tests and failed on its first real edit, because the stub returned what each test configured. Proposed addition to 2.26 or the `test-audit` gate: when behaviour depends on what an external service stores or returns, the fake's answer is checked once against a read-back from the real service, and the test says where its expected value came from.
2. **Claims about failure handling.** For the third run in a row a sentence about what happens on failure was false (`CLAUDE.md:74`, `:78`). Each was written from the exceptions the code catches, not from the ways the remote can fail. Proposed for 2.12: a sentence that says "X fails closed" or "Y is not retried" names the failure modes it was tested against.
3. **The rerun rule, fourth data point.** D3, D4 and the sweep halves of D1 and D2 came in with the fixes for the second intake.
4. **Auditing your own fix.** This intake followed a fix in the same session. The fresh subagent found D3, D4 and D6, none of which the author had listed. Proposed for the skill: when the intake follows a fix made in the same session, the `improve` pass goes to an agent that is given the code and not the author's notes.
5. **2.25 where issues are off.** On a fork with issues disabled the README is the only accepted place. The row could say so. It could also say whether a defect found while fixing another, and named in the PR that shipped, counts as "known": this run read it as yes.
6. **2.7 and failure branches.** The row passed last run with the same branch untested. It failed this run because the branch is now known to be reachable. Proposed wording: a failure branch on a write path is a data-loss path whether or not it has been seen to fire.
7. **2.21 and what counts as a ruling.** The owner approving a PR description is thinner than the owner choosing between stated options. This run graded it "PASS (ruled, thinly)". The row could require that a behaviour change be put as a question.
8. Still open from earlier reports: the PaaS wording for 1.2, the scope of 2.1, 2.15 on silence, a lighter row for third-party personal data under 1.3, and 2.8 on single-file apps.
