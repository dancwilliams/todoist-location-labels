## 4. Bugs

**F1. An edit that changes only the coordinates deletes every reminder of the mapping and re-adds none, and answers 302.** `reminder_is_at` matches on name, trigger and radius (`app.py:305-309`, `match_key` `:293-295`); the route sweeps whenever the whole five-tuple differs (`:505`), lat and long included. #49's `already` set uses the same matcher against `new_place` (`:328-330`). When only the coordinates change, `match_key(old_place) == match_key(new_place)`, so every reminder in `matched` is also "already at the new place": the loop sends a delete per reminder and skips every add (`:331-334`), logs `sweep: N re-adds skipped` (`:335-336`), `todoist_run_commands` answers all `ok`, the route saves the new coordinates and redirects. Reproduced (`probe_sweep6.py` scenario D): mapping Home at lat 1.0 with reminders on tasks 900 and 901, POST the same address, trigger and radius with lat 9.0 → `302`, `reminders={}`, `INFO sweep: 2 re-adds skipped`. On the pre-#49 `app.py` (60e1a86 checked out for the run, then restored) the same POST leaves both tasks with a reminder: delete and add per task, the add carrying the new coordinates. Each reminder comes back only when its task next changes (the webhook adds it at the mapping's place, `:603-622`). The user sees success. **Trigger from the UI:** `address` is the Places text and lat/long are hidden fields filled from `place.geometry` (`templates/index.html:238-239`, `:279-280`); picking the same address again after Google has moved its geometry, or a suggestion with the same text and other coordinates, is a coordinate-only edit. Frequency unknown (Not checked); the sweep's reason to exist is exactly that a coordinate change must move the reminders, since Todoist stores `loc_lat`/`loc_long` per reminder. **Fix (S):** skip the dedupe when the match key does not change — `already = {...} if new_place is not None and match_key(old_place) != match_key(new_place) else set()` — because then nothing can be "already at the new place" that is not also being deleted; equivalently, build `already` from reminders not in `matched`. Plus the test the plan lacked: an edit that changes only `lat` sends one delete and one add per task, the add carrying the new `loc_lat`. Regression introduced by #49, outside the three stub cases the plan traced (all changed the name). Confidence HIGH on mechanism and reproduction; frequency LOW to UNKNOWN.

**F2. After a skipped re-add, a delete/add pair can straddle a batch boundary, and a failure of the later batch loses that task's reminder until its task changes.** Before #49 the command list was strictly alternating (`del, add, del, add, …`), so with `SYNC_BATCH` even (100, `:95`) no pair was ever split — the invariant `CLAUDE.md:81` states. A skip removes one `add`, every later pair shifts by one, and the batch loop cuts at fixed offsets (`:260-261`). If a later batch raises (`:262`, a `ConnectionError`, a 5xx after retries, a malformed answer), `todoist_run_commands` propagates, the route keeps the mapping and says "Submit the same change again" (`:508-512`, `:103`). The task whose delete went and whose add did not now holds nothing at either place: the resubmit neither matches nor skips it, saves the mapping, and answers 302. Reproduced (scenario E, `SYNC_BATCH=2`): task 900 already at Oak, 901 and 902 at Home, second request raising → `502`, `{'900': ['Oak'], '902': ['Home']}`; resubmit → `302`, `{'900': ['Oak'], '902': ['Oak']}`, 901 empty. The webhook restores it on 901's next change (`:603-622`), as in the `ADDS_REFUSED` case, but the page said the opposite. Needs a skip, more than 50 tagged tasks on one label, and a failed later request: never observed, and the window has never shown a multi-batch sweep. **Fix (S):** emit the pairs first and the lone deletes last, so the pairs occupy an even-length prefix and never straddle; or batch by pairs. Regression introduced by #49. Confidence HIGH on mechanism; frequency LOW.

**F3. A resubmit to a place other than the half-applied one strands the reminders at the intermediate place.** After a refused delete (502, `SWEEP_FAILED`), N−1 tasks hold a reminder at the attempted place under a mapping that still says the old one. The page asks for "the same change" (`:103`); nothing stops a different one. The sweep matches only `old_place` (`:322`), the app stores no reminder ids (`CLAUDE.md:76`), and the intermediate place has no mapping, so no webhook can ever remove those reminders (`:593-600` deletes only what matches a mapping not on the task). Reproduced (scenario A): Home→Oak with 900's delete refused, then an edit to Elm → `302`, `{'900': ['Oak', 'Elm'], '901': ['Oak']}`; a webhook on 901 → `{'901': ['Oak', 'Elm']}`. Both Oak reminders fire forever. Pre-existing: the same state arose before #49, with duplicates on top. Two unobserved conditions (a refused delete, then a user ignoring the sentence). **Fix:** the only lever without stored ids is the user: a README clause ("the same change, not a different one") is S; prefilling the form with the failed target is M. Confidence HIGH on mechanism; frequency LOW.
