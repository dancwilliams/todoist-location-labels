## 4. Bugs

**B1. A sweep with one refused add leaves the other tasks moved, and a task that changes before the resubmit ends up with two reminders.** Todoist applies each sync command on its own and reports each status; `todoist_run_commands` raises when any is not `ok` (`app.py:243-246`), the route answers 502 and keeps the old mapping (`:465-472`). By then every delete in the batch and every other add have been applied, so those tasks' reminders sit at the new place while the mapping says the old one. If one of those tasks changes before the user resubmits, the webhook reads its reminders (`:516`), finds none at the mapping's place, and adds one at the old place (`:566-579`). The resubmit then sweeps that one to the new place and the task carries two identical reminders. Reproduced in one batch of four commands with a stateful stub (`scratchpad/test_b1.py`, exit 0):

```
edit 1: 502 batches: [4] reminders: [('900', '2 Oak Ave')]
webhook for 900: 200 reminders: [('900', '2 Oak Ave'), ('900', 'Home')]
edit 2: 302 reminders: [('900', '2 Oak Ave'), ('900', '2 Oak Ave')]
```

Without the intervening task change the resubmit matches 0 of N and the lost reminder returns at the new place on its task's next change, which is the recovery the plan designed. The third report's D4 said "submitting the same edit again recovers"; that was true only in that order. Trigger: a refusal of one add in a sweep. The two refusals measured on 2026-10-05 are blocked by the form; the remaining candidates are the account's location-reminder limit (300) and a task deleted between the read and the write, neither observed. Fix: when every delete in the sweep was accepted and only adds were refused, save the new mapping anyway and answer 502 with the sentence as it stands; nothing is then at the old place, and the webhook re-creates the missing reminders at the new place. That also makes the README bullet exact. Test through `fake_todoist` with the stateful stub above. Effort S to M. Confidence HIGH on the mechanism; LOW on frequency (never observed).

**B2. Rows that share a match key are not refused after the fact, and a sweep of one takes the other's reminders.** The check at `app.py:449-458` runs on submission only; there is no constraint. Reproduced by the subagent with a second row inserted directly: editing label 10 swept `2 of 2` and moved label 11's task. Exposure: zero. The fix plan's Phase 0b counted `same_place_pairs` over `(user_id, btrim(name), loc_trigger, least(floor(radius), 255))`, the same key, and found 0 on 2026-10-05; every row saved since went through the check. Closed in the data. A unique constraint on `(user_id, name, loc_trigger, radius)` would make it structural; `radius` is a `Float` column holding whole numbers since #40, so the constraint would hold. Effort S. Confidence HIGH on the mechanism; not a production bug.

## 8. Standards feedback

The third report's D4 note "submitting again recovers" was carried into the plan unexamined. 3. **2.25 and defects found by the intake itself.** For the second run in a row 2.25 fails on a defect this report is the first to name. That is the row working as written. It could say so: a defect first named by an intake report fails 2.25 until the README or the fix lands, so the verdict is "not in the fold" by construction whenever an intake finds a shipped bug.
4. **2.12 and sentences about batching.** "In one batch", "in one request", "atomically" are claims about Todoist's behaviour as much as the app's. Proposed wording for 2.12: a sentence that says two operations happen together names the unit (one request, one transaction) and the size at which it stops being true.
