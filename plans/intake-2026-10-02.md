## 4. Bugs

Ranked by impact over effort. B0 is runtime-backed; the rest are confirmed by reading the cited lines unless marked hypothetical.

**B0. Tracing is dead: no span has been recorded or exported since the March migration.** Runtime-backed. The entrypoint is `opentelemetry-instrument gunicorn ...` (`Dockerfile:16`). Auto-instrumentation only installs a real `TracerProvider` through an `opentelemetry_configurator` entry point, and no installed package provides one: `grep -l opentelemetry_configurator <lock-exact venv>/*.dist-info/entry_points.txt` returns nothing, and `opentelemetry-distro` is absent from `uv.lock` (`grep -c 'name = "opentelemetry-distro"' uv.lock`: 0). Reproduced under the production lockfile: `opentelemetry-instrument python -c ...` reports `provider: ProxyTracerProvider`, `span recording: False`, and a 25 s gunicorn run with two requests and no `OTEL_EXPORTER_OTLP_*` set logs zero export lines. Production logs show the same silence (no export success, no "Failed to export", no localhost:4317; `fly logs --no-tail`, 100 lines). Before 0e08269 the Dockerfile ran `pip install honeycomb-opentelemetry --pre` (4f72fdc, 2023-11-29), whose distro supplied the configurator, the Honeycomb endpoint and the `HONEYCOMB_API_KEY` header; the migration commit removed it ("Replace archived honeycomb-opentelemetry with standard OpenTelemetry SDK 1.40") without adding `opentelemetry-distro` or the `OTEL_EXPORTER_OTLP_ENDPOINT`/`_HEADERS` secrets. Result: every `@tracer.start_as_current_span` in `app.py` is a no-op, the Flask/requests/urllib3/jinja2/logging instrumentors instrument into the void, `HONEYCOMB_API_KEY` and `OTEL_SERVICE_NAME` in Fly secrets are read by nothing, and Honeycomb has received nothing from this app for about six months (unconfirmed from the Honeycomb side). Two fixes, Dan's call: (a) add `opentelemetry-distro` to dependencies and set `OTEL_EXPORTER_OTLP_ENDPOINT=https://api.honeycomb.io` and `OTEL_EXPORTER_OTLP_HEADERS=x-honeycomb-team=<key>` as Fly secrets, then confirm a trace in Honeycomb; or (b) delete the twelve OpenTelemetry packages, the `tracer` decorators and the `opentelemetry-instrument` prefix, and the two unused secrets. Effort S either way. Confidence HIGH.

**B1. Webhook accepts unsigned requests.** `app.py:366-384`: `/webhook` reads `initiator["id"]`, loads that user's stored OAuth token and acts on Todoist with it. Todoist signs every delivery with base64(HMAC-SHA256(client_secret, body)) in `X-Todoist-Hmac-SHA256`; the handler never reads the header. Scenario: anyone who knows a victim's numeric Todoist user ID POSTs `{"event_name":"item:updated","initiator":{"id":"<victim>"},"event_data":{"id":"<task>","labels":[]}}` and the app deletes the victim's location reminders on that task using the victim's token (`:425-439`), or adds reminders with crafted labels. The plan deferred this ("future improvement", `plans/2026-03-20-...md:49`); it is a security measure at a trust boundary, so it is reported as a bug, not taste. Fix: `hmac.compare_digest(base64.b64encode(hmac.new(client_secret.encode(), request.get_data(), "sha256").digest()), header)` before `request.json`; abort(401) otherwise. Effort S. Confidence HIGH.

**B2. Duplicate label mappings are invisible and undeletable.** `LocationLabel.label_id` has no unique constraint per user (`app.py:70-74`); `create_label_location` inserts without checking (`:343-363`); the form offers every label including ones already mapped (`templates/index.html:178-180`). The index view builds a dict keyed by label id, so one row wins (`app.py:248-250`); the delete route removes `.all()[0]` in unspecified order (`:330`); the webhook iterates every row (`:443-447`). Scenario: a user adds label X twice with two addresses; the UI shows one; deleting it leaves the other, which keeps creating reminders on every task tagged X with no way to remove it short of the database. Fix: `UniqueConstraint("user_id", "label_id")` plus upsert-or-reject in create. Effort S (schema change on a live Postgres: needs a migration step, so effort S but risk MED). Confidence HIGH.

**B3. Pool configuration is dead and documented as live.** `app.py:47-49` sets `SQLALCHEMY_POOL_SIZE`, `_TIMEOUT`, `_RECYCLE`; Flask-SQLAlchemy 3.1.1 reads only `SQLALCHEMY_ENGINE_OPTIONS` (verified in the installed `extension.py`). The engine runs with SQLAlchemy defaults (pool 5, no recycle). CLAUDE.md:70 states the opposite. Impact today is low because `pre_ping` (`:42`) is the setting that actually handles Fly Postgres connection drops. Fix: fold the three values into the `SQLALCHEMY_ENGINE_OPTIONS` dict and correct CLAUDE.md. Effort S. Confidence HIGH.

**B4. Delete route crashes before its 404 and is a state-changing GET.** `app.py:330` `.all()[0]` raises IndexError on an unknown id, so `:331-332` never runs and the user gets a 500. The route is a GET (`:325`) guarded only by a client-side `confirm()` (`index.html:158`); with Flask's default cookie policy (browsers apply SameSite=Lax) a top-level cross-site link to `/delete_label_location/<id>` deletes a logged-in victim's mapping. Fix: `first_or_404()` scoped by `user_id`, and make the route POST with a form. Effort S. Confidence HIGH.

**B5. Unhandled KeyErrors return 500.** `app.py:277` `session["oauth_secret_state"]` when the session expired or a visitor hits the callback cold; `:321` `del session["user_id"]` on `/logout` when not logged in. Fix: `.get` and `.pop`. Effort S. Confidence HIGH. Impact low.

**B6. OAuth token exchange has no timeout.** `app.py:284-292` `requests.post` without `timeout=`, unlike every other call (`:127`, `:178`). A hung Todoist endpoint holds a gunicorn sync worker until the worker timeout. Effort S. Confidence HIGH. Impact low.

**B7. Retry on every HTTPError.** `app.py:117-123` retries 401/403/404 three times with 2 s waits. A user who revoked the app pays 4 s and three error log lines per webhook forever, since the token is never cleared. Fix: retry only on 5xx/429, and on 401 null the token. Effort S. Confidence HIGH. Impact low.

Benign, but the message says "intermittent failures" and the first visitor after idle may get one. Fix: `grace_period = "15s"`. Effort S.

## 6. Opinions

Tier 3 and taste. Not defects.

- `User.query.get(...)` (`app.py:91, 241, 306`) is the legacy Query API; SQLAlchemy 2.0 spells it `db.session.get(User, id)` and will warn. Same behaviour.
- Twelve OpenTelemetry packages on a one-file hobby app is a lot of surface for Dependabot to churn (13 OTel PRs in one day in March); B0 shows the surface has been paying nothing back. Honeycomb tracing is a stated choice (CLAUDE.md:66, 72), so whether to repair or remove it is Dan's call, recorded under B0.
- Bootstrap 4.0.0-beta.2 (2017) from maxcdn with SRI hashes. All five CDN URLs answered 200 today. It works; it is a 2017 beta.
- `trigger` and `radius` form values (`app.py:347, 351`) are not validated: `radius=abc` returns a 500 instead of a 400. The input is the user's own mapping; UX, not security.
- Logging mixes f-strings (`:99, 103, 155`) with %-style (`:130, 150`). Pick one.
- The webhook does a full reminders sync (`sync_token="*"`, `:174, 186`) on every event. Fine at this scale; a per-user sync token would be the upgrade if webhook latency ever matters.
- `oauth_redirect` sends `redirect_uri=url_for("authorize")` (`:290`), which is not the callback URL. Todoist evidently ignores it (the flow works in production). Harmless, but it reads like a bug to the next reader.
- gunicorn 25 opens a control socket in the working directory at boot (`/app/gunicorn.ctl` in the image). Harmless; `--no-control-socket` if it ever bothers anyone.

**B12. A Todoist API failure during a webhook is treated as "task has no labels" and deletes reminders.** `todoist_get_labels` (`app.py:140-156`) and `todoist_get_reminders` (`:183-190`) swallow `RequestException` and return `[]`.
